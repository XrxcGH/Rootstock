# first-mechanism

The smallest set of files that makes one mechanism move: an elevator on a single TalonFX, homed by
current spike, with two named positions and manual control on the left stick.

```
src/main/java/frc/robot/
  RobotConfig.java       the elevator, declared as data
  RobotContainer.java    construction, registration and the driver's buttons
  Robot.java             the base class
  Main.java              WPILib's entry point, unchanged
```

## How to use it

This is **not** a Gradle project. It is a `frc/robot` package you copy into a robot project you
already made, because the build side of the story is four lines and belongs in one place rather
than duplicated into every example.

1. Follow [`docs/getting-started.md`](../../docs/getting-started.md) through step 4. That is where
   you make the WPILib project, install the AdvantageKit vendordep, and point your
   `settings.gradle` at your clone of this repository with `includeBuild`.
2. Copy the four files in `src/main/java/frc/robot/` over the ones GradleRIO generated.
3. Change the CAN ID, the reduction, the axis and the soft limits to match your robot.
4. `./gradlew simulateJava`.

The same four files are printed inline in getting-started step 5, so that a reader on GitHub can
see them without navigating. **These are the copies that were compiled**; if the two ever
disagree, believe these.

## What to look at, in order

**`RobotConfig.java`.** The gearbox and the geometry are declared once each, and nothing anywhere
else multiplies by a ratio. Read the derivation dump `RobotContainer` prints and check the
travel-per-rotation line against CAD. This elevator should report one output rotation as 11 inches, printed as
`0.279400 m`: a 22-tooth number 25 sprocket is 5.5 inches of chain per turn, doubled by two
cascade stages.

**`RobotContainer.java`.** `RootstockRegistry.addAll(...)` is the one call that attaches telemetry,
the health monitors, the pit self-test, live tuning and the CAN ID conflict scan, and it is also
where config validation runs. Everything else in the file is ordinary WPILib command binding,
because a `PositionMechanism` is an ordinary `Subsystem`.

**`Robot.java`.** Three lines that matter: which `LogConfig` factory you pick, constructing the
container, and calling `lifecycle().init()` last.

## What you should see

In simulation, `Gains.UNTUNED` resolves to a first guess derived from the declared carriage mass,
so pressing **Start** homes the elevator and pressing **Y** raises it. On real hardware the same
config refuses closed-loop control and raises an alert telling you to run the tuning wizard;
homing and manual control still work. That is deliberate, and
[`docs/troubleshooting.md`](../../docs/troubleshooting.md) has the rest of it.

## Verifying these files

They are not on the Gradle build, so they can drift. This is the command that checks them, and it
was run against these exact files:

```bash
cd /path/to/Rootstock
javac -cp "$(cat .cp-core.txt)" -d /tmp/probe examples/first-mechanism/src/main/java/frc/robot/*.java
# exit 0
```

`.cp-core.txt` holds the core module's compile classpath on one line. It is regenerated by the
build. If that command fails, these files are stale and the failure is a bug worth reporting.
