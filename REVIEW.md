# PumpkinLib Design Review — Synthesis of Six Independent Expert Reviews

**Date:** 2026-08-07 · **Scope:** all ten documents (~22,800 lines), reviewed against the four binding maintainer decisions of 2026-08-07 (full scope in v0.1; template-first delivery; AdvantageKit required; BSD-3-Clause).
**Method:** six independent lens reviews, synthesized after independently re-reading README.md and DESIGN.md, re-checking contested anchors in all six domain docs, and re-verifying contested vendor-API claims against primary sources (CTRE Phoenix 6 javadoc, AdvantageKit LICENSE).

---

## 1. Verdict

**Not ready to implement from — but closer than the finding count suggests, and fixable entirely in the documents.** The architecture is sound, the honesty apparatus is the best any reviewer has seen in an FRC project, and the four maintainer decisions were applied thoroughly and candidly to README, ROADMAP, DECISIONS and most of DESIGN.md. The failures are of two kinds. First, **propagation**: the 2026-08-07 consistency sweep that DESIGN.md §16 item 4 declares DONE never touched `design/02-tuning.md` (the sweep list in item 4 literally omits it), so the tuning doc — the spec for the library's flagship feature — still defines a 12-field `Gains`, a deleted `LoopLocation`, a `TuningTarget` incompatible with the one DESIGN.md §11b compiles, and "AdvantageKit: optional"; and several corrections one domain doc ordered in another (the MegaTag2 gyro-offset contract, the drive-to-pose tolerance, the D17 vision seam) were specified but never applied at the receiving end. Second, **API truth**: the exact defect class the previous adversarial review flagged recurred one level down — the flagship Phoenix goal seam calls `MotionMagicVoltage.withVelocity()`, which does not exist (verified against CTRE's javadoc); the flagship REV backend commands a 60× cruise velocity; and the vision domain's terminal alignment controllers reintroduce, twice, the sign-flipped drive-away-from-target loop that design/05 §9.1 fixed and test-pinned. Ten blocking and roughly twenty-two major findings survive verification. None requires re-architecting; nearly all are one-commit document fixes plus the pinning tests the docs already promise. Fix the blocking list before writing any code — M1 through M7 would otherwise be built directly on top of contradictory specs.

### B2. The flagship Phoenix goal seam calls methods that do not exist
**File:** `design/01-core-mechanisms.md`; **anchors:** line 1287 (`m_mmVoltage.withPosition(outputRot).withVelocity(outputRps)` and the `m_mmExpo` twin), lines 1273–1280 (`m_mmDynamic.withVelocity(outputRps).withVelocity(cruise)` — chained twice), line 3029 (§6.4 repeats "`MotionMagicVoltage.withVelocity(...)`" for the field-locked turret).
**Problem:** **Verified against the CTRE javadoc:** `MotionMagicVoltage` and `MotionMagicExpoVoltage` have no `Velocity` field and no `withVelocity` method. The `ON_MOTOR_PROFILED` branch of `setPositionGoal` — the library's headline seam — does not compile. On `DynamicMotionMagicVoltage`, `Velocity` **is the profile cruise velocity**, so the first chained `.withVelocity(outputRps)` (intended as goal velocity) is silently overwritten by the cruise ceiling, and the field-locked turret's counter-rotation term is silently dropped — the exact TurretIONeo silent-drop defect this section claims to fix. This violates the doc's own header promise that every vendor API name was read from the javadoc or marked `[UNVERIFIED]`. Found by lens 3; independently re-verified in this synthesis.
**Fix:** Fold the goal-velocity term into the arbitrary feedforward: `ff += kV_phx * goalRps` volts via `withFeedForward` (mirroring the REV fallback §6.4 already specifies), or route velocity-carrying goals to `PositionVoltage` (which genuinely has `withVelocity`). Delete the first `withVelocity` on the Dynamic path. Set `MotorCapabilities.positionGoalVelocity()=false` for MotionMagic request paths and have `describe()` print which path serves the field lock. Add a compile-against-vendor test for every request-builder chain in §3.5.6.

### B3. Both vision terminal controllers drive the robot away from the target — the previously-fixed sign-flip bug, reintroduced
**File:** `design/03-vision.md`; **anchors:** line 2379 (§13.4: `errorXY = goal.minus(current)` paired with `m_translationController.calculate(errorNorm, 0.0) * ffScale`), line 2420 (§13.5 `alignToTag`: same pairing).
**Problem:** WPILib `PIDController.calculate(measurement, setpoint)` computes error = setpoint − measurement, so `calculate(errorNorm, 0.0)` is **negative** while approaching. Pairing that negative scalar with a robot→goal direction vector commands velocity **away** from the target, accelerating. `design/05` §9.1 names this exact pairing as the fatal one and mandates `current.minus(target)` — with a regression test — yet design/03's §13.4 (`driveToPose`, `alignToNearest`) and §13.5 (`alignToTag`, the command the doc calls "the command that makes the compete-against-world-class-teams claim honest") both ship the fatal pairing. The omega channel in the same twelve lines uses the opposite (correct) argument order, proving it's a bug, not a convention. Secondary defects in the same blocks: `ffScale` multiplies the **feedback** term instead of the feedforward, creating a dead zone exactly equal to each command's own tolerance (2 cm / 5 cm), and `m_translationProfileVelocity` is never declared or seeded. Found by lens 6; pairing re-verified against design/05 §9.1's own prose.
**Fix:** Rewrite both blocks to design/05 §9.1's audited pattern (`current − goal` direction with the negative scalar; `ffScale` on the profile-feedforward term only; declared, seeded `ProfiledPIDController` state). Add commanded-velocity-**direction** assertions (equivalents of `drivesTowardTheTarget` / `drivesTowardTheTargetOffAxis`) to §16's test table — the specified `AlignToTagTest` pins error computation only and would not catch this.

### B5. The flagship REV backend commands a 60× cruise velocity
**File:** `design/01-core-mechanisms.md`; **anchor:** lines 1410–1412 (`.cruiseVelocity(u.toOutputRps(...) * 60.0) // RPM` and the matching `maxAcceleration * 60.0`).
**Problem:** The same `buildConfig` sets `velocityConversionFactor` so the controller works in output rot/s (line ~1382); per REV's MAXMotionConfig documentation, `cruiseVelocity`/`maxAcceleration` are "natively RPM but will be affected by the velocity conversion factor." With the factor applied, the `*60.0` double-converts — a 60× too-fast cruise command, an effectively unconstrained profile on a REV elevator or arm. This is the precise unit-error class (41× `/360`, 57.3× `RIO_FULL`) the library's core pitch is eliminating, and it is not marked `[UNVERIFIED]`. Found independently by lenses 1 and 3.
**Fix:** Delete both `*60.0` factors (units follow the configured conversion factor); mark the row for a `SparkSim` pinning test (drive a MAXMotion move, assert profile velocity ≈ configured cruise), mirroring the `SparkSim.iterate` test the doc already mandates.

### B6. The flagship elevator kG derivation is ~2.2× low — in a table claimed to be CI-asserted
**File:** `design/01-core-mechanisms.md` §5.4 (and §3.5.7's `describe()` block; `DESIGN.md` §10A.1 reference-gains block); **anchor:** `kG | 24 lb carriage, 2:1 cascade, 12:1, Kraken kT ≈ 0.0194, R ≈ 0.0328, ×2 motors | 0.15 V`.
**Problem:** Recomputed in this synthesis: 24 lb → 106.8 N; effective radius incl. cascade = 0.280293/(2π) = 0.0446 m → 4.77 N·m at the drum; ÷12 ÷2 motors = 0.199 N·m/rotor; ÷0.0194 = 10.2 A; ×0.0328 Ω = **0.34 V**, not 0.15. The 0.15 figure is consistent with dropping the cascade ×2 — the exact bug class `LinearAxis` exists to prevent — while the adjacent stall-force row uses the correct radius, so the table is internally inconsistent. The doc says these numbers "are recomputed by describe() and asserted by DescribeSnapshotTest." Found by lens 1; arithmetic re-verified.
**Fix:** Recompute the row to ≈0.34 V (or, if 0.15 V is 8793's measured value, remove it from the *derivation* table and label it measured-not-derived); update §3.5.7 and DESIGN.md §10A.1 to match; make `DescribeSnapshotTest`'s expected block the recomputed one.

### B9. The byte-budget governor demotes replayed inputs, breaking the byte-identical replay guarantee decision 3 was spent to buy
**File:** `design/04-telemetry-replay-viz.md`; **anchor:** lines 575–576 (§2.7 demotable table: `Inputs/SupplyCurrentAmps` and `Inputs/TempCelsius` marked `Demotable.YES`).
**Problem:** Two of the five demotable keys are replayed **inputs** inside hand-written `LoggableInputs` structs. In replay, `fromLog` returns stale values for 4 of 5 cycles while the real robot read fresh ones; every derived output (design/06's power/brownout/thermal monitors explicitly consume these per G8) diverges — violating §2.5A's byte-identical guarantee, which §5.6's boundary handling does not cover (it excludes only the demoted key itself, not downstream outputs). Found by lens 3.
**Fix:** Restrict `Demotable.YES` to output keys. Keep `Inputs/SupplyCurrentAmps` at full rate (it is replay-load-bearing) and demote a derived STANDARD output mirror instead, or shrink it structurally (leader scalar + follower array). Update the §2.7 table, the `logBudget` example, and §5.2's manifest example (which demotes `ModulePositions` — an output — and is fine).

## 4. Major findings

### Cross-cutting / integration

**M1. `PumpkinRobot`/`PumpkinLifecycle` — the class MD3 itself created — is spelled three incompatible ways.** DESIGN §10A.4 (line ~1021) gives `PumpkinRobot` a `Consumer<LogConfig>` constructor; design/01 §1.1a (lines 241–256) shows no constructor, hard-coding `PumpkinLifecycle.create(LogConfig.defaults())`, in package `org.pumpkinlib` (D13 says `org.pumpkinlib.core`); design/06 §13 shows `super()` "no arguments." README line 178 calls `PumpkinLifecycle.create()` no-arg vs D29's `create(LogConfig)`. design/01 line 265 introduces `LogConfig.adoptExistingLogger()` for the existing-`LoggedRobot` case while DESIGN §11b/README use `defaults()` in the identical scenario — leaving "who calls `Logger.start()`" ambiguous (a double-start crash in the making). *(Lenses 1, 2.)* **Fix:** add a §16 item 5 sub-item; pick one spec (both constructors on `org.pumpkinlib.core.PumpkinRobot`; `create(LogConfig)` as the only factory; `adoptExistingLogger()` required when the team already started the Logger) and propagate to all four locations.

**M2. `Reduction.ofTeeth(int driving, int driven)` parameter names are inverted relative to every documented usage.** design/01 lines 1733–1734: `ofTeeth(58, 10)` is used everywhere to mean a 5.8:1 **reduction**, which requires the first argument to be the *driven* (output) gear. As declared, a faithful implementation makes the flagship arm a 65× speed-up. (Its javadoc example also still prints 34.126 — see B7.) *(Lens 1.)* **Fix:** rename to `ofTeeth(int drivenTeeth, int drivingTeeth)` (same for `then`) plus a test pinning `ofTeeth(58,10).rotorPerOutput() == 5.8`.

**M3. `robotInit()` is simultaneously banned and used by the library's own front door.** DESIGN line 137 and ArchUnit rule 5 (line 700) declare `robotInit()` a 2027-removed API that is "not used"; yet `PumpkinRobot` (design/01 line 244), `PumpkinLifecycle`'s surface (D29), §10A.4, §11b's CI-compiled fixture, and README's adoption snippet all override or name it. *(Lens 1.)* **Fix:** move initialization into constructors (WPILib-recommended since 2024), rename `PumpkinLifecycle.robotInit()` → `init()`, scope rule 5 to overriding `IterativeRobotBase.robotInit`.

**M4. design/01 still describes three superseded architectures as current.** (a) §1.1a hooks javadoc (lines 218–220): "discovered by ServiceLoader... Unchanged by decision 3" — directly contradicting D26-as-amended (explicit in-jar list; ServiceLoader only for out-of-jar adapters). (b) §6.1/§6.7 still declare `Mechanism.simulationPeriodic()` and ship the `simulatedMotorVoltage()`/`updateSimulatedSensors()` call-site code D18 deleted outright (methods absent from the §3.3 `MotorIO` interface — the snippet cannot compile). (c) §10 item 1 (line 3913) describes permanent dual release lines ("Two release lines from day one") vs the M12-only dual-compile model docs 02/04 and ROADMAP §7.2 specify. *(Lenses 1, 3.)* **Fix:** three targeted rewrites, each pointing at the authoritative decision.

**M5. `MatchImpact` — mandatory at every alert call site per binding D10, "no default and no single-argument overload" — appears in zero of the five domain docs 01–05.** Grep verified in this synthesis: 0 matches in each. design/03 and design/05 declare and use two-argument `PumpkinAlerts.error/warning(group, text)` facades throughout. Every alert in five domains dodges exactly the question D10 exists to force. *(Lens 6, broadened here.)* **Fix:** sweep all five docs to `Alerts.error/warning/info(group, text, MatchImpact)` and annotate each call site (`GYRO_OFFSET_UNSEEDED`, MEGATAG2-orientation = `BLOCKS_MATCH`; `CALIB_REPROJ_HIGH`, `align.timeout` = `PIT_ONLY`); add to §16.

### Physics, safety, and control (design/01, design/02)

**M6. CAN-budget arithmetic is wrong by ~10×.** design/01 line 944: "800 frames/s of 8-byte payload ≈ 0.6% of a 1 Mbps rio bus" — 800 × 64 payload bits = 5.1% payload-only; ~10.4% with framing/stuffing (~130 bits/frame). The error (treating bytes as bits) justifies the 100 Hz default; on a bus already carrying swerve at 60–80%, eight mechanisms at 100 Hz can saturate it — producing exactly the frozen-signal failures the library exists to prevent. Same error in the `describe()` output. *(Lens 3.)* **Fix:** recompute both printed numbers; print a true aggregate frame budget in `describe()`; measure 8793's bus before freezing the default (open question 14 already proposes this).

**M7. Jerk is passed to Phoenix unconverted.** design/01 line 1134: `MotionMagicJerk = constraints().jerk()` raw (user units/s³) while cruise/accel on the adjacent lines are converted — off by 360 for rotary, 1/travel-per-rot for linear; same omission on the Dynamic path. *(Lens 3.)* **Fix:** add `MechanismUnits.toOutputRps3()` and use it at both sites; extend `UnitsContractTest` with a jerk row.

**M8. The wizard's gravity handling has four real safety/physics holes** (design/02 §6–§8, all from lens 3, all consistent with the doc's own reasoning elsewhere):
- **kG drift probe silently reports kG=0 on brake-mode or high-reduction gravity mechanisms** (line ~2164): the 0.5 s zero-voltage probe cannot see drift when brake mode or gearbox stiction holds the mechanism; the wizard then measures gravity as friction (kS ~10× large — §8.5's own warned failure). Fix: read back idle mode, temporarily coast under supervision, and never take the kG=0 shortcut for ELEVATOR/ARM archetypes.
- **Supervisor `abort()` neutrals gravity mechanisms** (line ~1653), contradicting the doc's own taper note ("tapering to zero is *releasing the mechanism*") and `abortProbe`'s "hold at kG_best, do not release." A coast-mode arm drops onto its hard stop on every `ENABLE_RELEASED`. Fix: either pre-flight-require BRAKE for gravity archetypes, or bounded kG-hold-then-ramp on abort, with a `SafetyAbortTest` gravity case.
- **`SafetyEnvelope.derive`'s guard degenerates when `softMargin ≥ 5%` of travel** (line ~1552): `guard = max(softMargin, 0.05·range)` makes the supervisor band *equal* the device soft-limit band, falsifying the trips-first guarantee — the same failure revision 2 fixed at the zero-margin end. The test only exercises 2% margins. Fix: `guard = softMargin + max(0.03·range, floor)`; add test cases at 5/10/20% margins.
- **`kGprior` divides by `motorCount` while prescribing an n-motor `DCMotor`** (line 1497–1500): WPILib's `getKrakenX60Foc(n)` leaves Kt unchanged and scales rOhms by 1/n, so Kt/R already carries ×n; the explicit ÷n makes the prior n× low on multi-motor mechanisms → bracket exhaustion on healthy hardware. Fix: delete the explicit factor, require the real motor count in `PlantPrior.motor`, pin with a 2-motor sim test. *(Adjudicated against lens 1's approval — see §8.)*
- Additionally: **`probe()`/`recentre()` are written as blocking while-loops** in a codebase that bans threads and drives steps from `periodic()` (§5.6 rule 3), with no `supervisor.check()` and no timeout on `recentre()`.
